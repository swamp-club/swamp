# Agent sessions

An agent session record says what one coding-agent session did in a swamp repo.
It lists the session's turns and tool calls, labels each call as using swamp, going
around it (a bypass), or neither, and carries findings that say what to
tune. The agent-sessions extension writes one record per session as ordinary
repo data; the dashboard's agent sessions page reads it (swamp-club#4154). The
extension imports the harnesses' own session files (Claude Code transcripts,
Codex rollouts), so no hooks or setup are needed.

The record is a read model built per session. It is not the observation event
stream or its OTEL mapping from the agent observation exploration; those are
designed separately, and that event schema must carry the user on every event.

## The record

The schema is `AgentSessionRecordV1Schema` in
`src/domain/agent_sessions/session_record.ts`, and core owns it. Extension
authors get its JSON Schema at
[`agent-session-record.schema.json`](./agent-session-record.schema.json). It is
generated by `deno run agent-session-schema`, and
`session_record_json_schema_test.ts` fails when the file drifts. Nothing is
published to a package until the extension is published.

| Level   | Fields                                                                                                                                                               |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session | `schemaVersion`, `id`, `repo`, `harness` (a slug), `harnessVersion`?, `model`, `startedAt` (ISO 8601 UTC), `swampUserId`?, `swampUsername`?, `parentSessionId`?, `importerVersion` |
| Turn    | `n`, `start`, `end`, `tokens` (`input`, `output`, `cacheRead`, `cacheWrite`), `calls`                                                                                |
| Call    | `id`, `tool`, `toolKind`, `start`, `end`, `ok`, `exitCode`?, `text`, `label` (`swamp`, `bypass`, `neutral`), `category`, `rule`, `swampSpans`?                        |
| Span    | per swamp command: `offset` from the call's start, then `spans` of `name`, `start`, `duration`, `depth`, `error`                                                     |
| Finding | `severity` (`high`, `medium`, `low`), `title`, `detail`, `tune`, `callIds`                                                                                           |

Turn and call times are milliseconds from the session's start. `toolKind`
maps each harness's tool name to one canonical set; a name with no mapping
is `unknown`. Findings are plain text, and every `callIds` entry names a call
in the same session.

**No transcript content.** Prompts and replies are never part of the record.
`text` holds only the redacted target of a call: a command line, a path, a
skill name or a URL. Text the model wrote, such as a subagent's description
or a search query, never goes in it. Every object is strict, so a record
carrying a field the schema does not name is refused, not kept. Redaction is
the extension's job.

**Size.** Every string has a maximum length and every list a maximum count
(`AGENT_SESSION_LIMITS`). A typical session is 25–250 KB; the longest the
prototype saw had 169 calls over 17 turns, far inside the limits.

## Identity

`swampUserId` is the swamp-club user id, the `id` from `/api/whoami`. It is the
same value serve uses as a user principal's OAuth `sub`, and it is the only
identity meant for access decisions. `swampUsername` is a display label taken
at import time. A rename on swamp-club can make it stale, which is why serve
pins the usernames in grant files to subs
([access-control](../enablers/access-control.md#usernames-in-grant-files)).
Storing an account id is a deliberate exception to the exploration's rule
that drops identity attributes, because per-user access needs a stable key.

Both fields are optional. The importer gets the id from `whoami`, because
local login (`auth.json`) stores only the username. Offline imports leave both
fields out. A collective API key names a collective, not a person, so its imports
leave them out too: `whoami`'s `collectiveId` never goes in `swampUserId`.

Both fields are attribution, not proof: whoever writes the record sets them.
They cannot back an "only your own sessions" guarantee until a later change
ties them to the writing principal, for example serve stamping the id from the
caller on a forwarded write.

## One item per session, and how the page finds it

Each session is one data item named `agent-session-<harness>-<session id>`
(`agentSessionDataName`). Re-importing writes a new version of the same item.
The extension's output spec sets two tags: `type: agent-session`, which
replaces the writer's own `type: resource`, and `swampUserId`.

The page lists sessions with the dashboard's existing `data.query` and the
predicate `tags.type == "agent-session"` (`AGENT_SESSION_QUERY_PREDICATE`).
It needs no new filter. `data.query` drops records the viewer may not read
before it applies the limit, so a page of results always reflects readable
sessions. `data.search` also takes a tags filter, but it applies its limit
before its read filter, so the page does not use it.
`integration/agent_session_discovery_test.ts` pins this contract.

A tag is a hint for finding records; it does not prove who wrote one. The
page validates every record's content with `readAgentSessionRecord` before
showing it.

## Versions

`schemaVersion` is in every record from version 1. `readAgentSessionRecord`
never throws, so one bad record cannot fail the page. A record it cannot read
is skipped with a note that names field paths and never field values:

| Reason    | When                                                    | Note tells the viewer to |
| --------- | ------------------------------------------------------- | ------------------------ |
| `newer`   | the version is above what this swamp reads              | upgrade swamp            |
| `older`   | a version this swamp no longer reads                    | re-import the session    |
| `invalid` | no integer `schemaVersion`, or content fails the schema | report the bad record    |

The page shows how many sessions it skipped and why. It never prompts for a
re-import. While version 1 is the only version, nothing is `older`.

A new field, even an optional one, is a new version, because version 1
refuses fields it does not name.

**Reading it in the page.** The dashboard has no `zod` dependency, and it
copies domain functions it needs, pinning the copy with a test
(`packages/dashboard/src/views/report_name.ts`). The page (swamp-club#4155)
either adds `zod` and imports this module, which has no Deno or Node APIs, or
copies the reader with a test that pins the copy.

## Access

Today a data read is authorized on the behavior that owns the data: its name
and tags, not the data item's own tags. A grant can therefore show or hide a
whole importer's sessions, but cannot yet say "only your own". The
`swampUserId` tag is written now so that a later access change can let a
condition compare it with `principal.sub`, with no change to the record. That
works when serve uses OAuth. Under `--auth-mode token` a user principal is a
username, so that mode would need a mapping.

## Sync

Session data is written under `data/`, which is in
`DEFAULT_DATASTORE_SUBDIRS`, so it syncs to a shared datastore by default.
That is accepted while the extension is unpublished, because only its authors
have session data. It must be settled before the extension is published,
together with the exploration's decision on where traces live. A user can
already keep sessions out of a shared datastore with an `exclude` pattern in
its config.
