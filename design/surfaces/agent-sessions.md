# Agent sessions

An agent session record says what one coding-agent session did in a swamp repo.
It lists the session's turns and tool calls, labels each call as using swamp, going
around it (a bypass), or neither, and carries findings that say what to
tune. The agent-sessions extension writes one record per session as ordinary
repo data; the dashboard's agent sessions page reads it (swamp-club#4154,
version 2 from swamp-club#4178). The
extension imports the harnesses' own session files (Claude Code transcripts,
Codex rollouts), so no hooks or setup are needed.

The record is a read model built per session. It is not the observation event
stream or its OTEL mapping from the agent observation exploration; those are
designed separately, and that event schema must carry the user on every event.

## The record

The schema is `AgentSessionRecordV2Schema` in
`src/domain/agent_sessions/session_record.ts`, and core owns it. Extension
authors get its JSON Schema at
[`agent-session-record.schema.json`](./agent-session-record.schema.json), and
the list summary's at
[`agent-session-summary.schema.json`](./agent-session-summary.schema.json).
Both are generated by `deno run agent-session-schema`, and
`session_record_json_schema_test.ts` fails when either file drifts.

Nothing is published to a package while the extension is a prototype. The
extension keeps its own copy of the schemas, `agentSessionSummary` and
`agentSessionTags`, and checks that copy against the two checked-in JSON
Schemas. A copy can still drift on the rules the JSON Schema cannot express,
so a record that passes the JSON Schema can still be skipped as `invalid`:

- every call id is unique within the session;
- every finding's `callIds` entry names a call in the session;
- a session has at most 20,000 calls in total;
- `subagentSessionId` is set only on a call whose `toolKind` is `subagent`;
- a call labelled `unlabeled` has no `category` or `rule`, and any other call
  has both;
- `agentId` and `agentType` are set only on a child session (one with
  `parentSessionId`);
- a child's `id` is the one `agentSessionChildId` gives for its
  `parentSessionId` and `agentId` (nothing checks this on read; the importer
  calls the helper).

The Zod schema is the authority. The extension's copy follows these rules by
hand.

| Level   | Fields                                                                                                                                                               |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session | `schemaVersion`, `id`, `repo`, `harness` (a slug), `harnessVersion`?, `model`?, `startedAt` (ISO 8601 UTC), `invocation` (`interactive`, `headless`, `unknown`), `swampUserId`?, `swampUsername`?, `parentSessionId`?, `agentId`?, `agentType`?, `importerVersion` |
| Turn    | `n`, `start`, `end`, `tokens` (`input`, `output`, `cacheRead`, `cacheWrite`), `calls` |
| Call    | `id`, `tool`, `toolKind`, `start`, `end`, `ok`, `exitCode`?, `text`, `truncated`?, `label` (`swamp`, `bypass`, `neutral`, `unlabeled`), `category`?, `rule`?, `subagentSessionId`?, `swampSpans`? |
| Span    | per swamp command: `offset` from the call's start, then `spans` of `name`, `start`, `duration`, `depth`, `error` |
| Finding | `severity` (`high`, `medium`, `low`, `info`), `title`, `detail`, `tune`, `callIds` |

Turn and call times are milliseconds from the session's start. `toolKind`
maps each harness's tool name to one canonical set; a name with no mapping
is `unknown`. Findings are plain text, and every `callIds` entry names a call
in the same session.

- `model` is absent when the session ended before any model reply, such as a
  cancelled `claude -p` or an aborted subagent.
- `invocation` says whether a person steered the session. A headless session,
  such as `claude -p` run by automation, has no person watching: its bypasses
  and failures come from the skills and rules alone and repeat on every run.
  `unknown` is for a harness that cannot tell.
- `label` is `unlabeled` on a call the importer wrote before any classifier
  labelled it (swamp-club#4156 imports, swamp-club#4157 labels). Such a call
  has no `category` or `rule`, so the page shows it as not classified rather
  than as `neutral`.
- `truncated` is `true` on a call whose `text` was cut to the 1000-character
  cap.
- A finding of severity `info` is not a problem to tune, for example one about
  swamp's own overhead ("teardown is 38% of each traced swamp command").
- Tokens count once per model reply. A harness that splits one reply over
  several records repeating the same usage (Claude Code shares
  `message.id` across them) counts that usage once.

The schema does not check that times are in order: an `end` before its
`start`, a call outside its turn, or turn numbers with gaps are all accepted.
Harness clocks and files are not always tidy, and refusing a whole session
over one bad time loses more than it protects. The page clamps what it draws
instead: a negative duration draws as zero.

**No transcript content.** Prompts and replies are never part of the record.
`text` holds only the redacted target of a call: a command line, a path, a
skill name or a URL. Text the model wrote, such as a subagent's description
or a search query, never goes in it. Every object is strict, so a record
carrying a field the schema does not name is refused, not kept. Redaction is
the extension's job.

**Size.** Every string has a maximum length and every list a maximum count
(`AGENT_SESSION_LIMITS`). The list limits apply to each list, so a session
also has a cap on its total calls (20,000). `readAgentSessionRecord` counts
turns and calls on the raw content before it parses anything, so a record over
either limit costs only that count; the schema checks the call cap again, ahead
of its call-id checks, for anyone who parses with it directly. A typical
session is 25–250 KB; the longest the prototype saw had 169 calls over 17
turns, far inside the limits.

## Subagents

A subagent is its own session record, a child of the session that started it.

- **Ids.** A harness's subagent id is unique only within its parent, so it
  never stands alone in the global name space. A child's `id` is
  `<parent id>_<hash>`, built by `agentSessionChildId`: the hash is the first
  32 hex digits of SHA-256 over `[parent id, agent id]` as JSON, and the
  parent id is cut so the whole id fits in 128 characters. The hash covers
  both ids in full and keeps the agent id's case, so ids that differ only in
  case, or in where a `_` falls, never meet. The helper is async (Web Crypto),
  for the importer only; the page follows `subagentSessionId` and never
  rebuilds an id. The child sets `parentSessionId` and `agentId` (the
  harness's own subagent id, unchanged), and may set `agentType`, the
  harness's subagent type (`general-purpose`, `Explore`, or a user-defined
  agent's name).
- **The link.** The parent's call that started the child has `toolKind:
  subagent` and `subagentSessionId` set to the child's id.
- **Loading.** The page loads a session's children with one bounded query on
  the `parentSessionId` tag (`agentSessionChildrenPredicate`) and reads a
  child's record when its call is expanded.
- **Findings.** A child's findings stay in the child's record, because each
  finding belongs to the agent that made the calls (swamp-club#4157). The
  parent's page shows them merged, and "Show calls" reaches the child's calls.
  Call ids are unique only within a session, so the page keys calls by session
  id plus call id.
- **Invocation.** A child copies its parent's `invocation`, and so its
  `headless` tag, even though harnesses mark every subagent non-interactive. A
  subagent started from an interactive session counts with that session.
- **Lifetime.** A child is written with the same lifetime as its parent, so
  neither outlives the other.
- **Timeline.** A child is drawn from its own `startedAt` and times, never
  inside the span of the call that started it. A background subagent's call
  ends at launch, a few milliseconds in, while the child runs for minutes.

## Identity

`swampUserId` is the swamp-club user id, the `id` from `/api/whoami`. It is the
same value serve uses as a user principal's OAuth `sub`, and it is the only
identity meant for access decisions. `swampUsername` is a display label taken
at import time. A rename on swamp-club can make it stale, which is why serve
pins the usernames in grant files to subs
([access-control](../enablers/access-control.md#usernames-in-grant-files)).
Storing an account id is a deliberate exception to the exploration's rule
that drops identity attributes, because per-user access needs a stable key.

Both fields are optional. The importer gets the id from `whoami`, because
local login (`auth.json`) stores only the username. Offline imports leave both
fields out. A collective API key names a collective, not a person, so its imports
leave them out too: `whoami`'s `collectiveId` never goes in `swampUserId`.

Both fields are attribution, not proof: whoever writes the record sets them.
They cannot back an "only your own sessions" guarantee until a later change
ties them to the writing principal, for example serve stamping the id from the
caller on a forwarded write.

## One item per session, and how the page finds it

Each session is one data item named `agent-session-<harness>_<session id>`
(`agentSessionDataName`). The data name is stored as a directory name, so:

- A harness slug cannot contain `_`, so one harness slug that prefixes
  another still gives a different name.
- Harness slugs and session ids are lowercase only, so two names never meet
  on a case-insensitive filesystem (macOS, Windows). The importer lowercases
  the harness's session id; the UUIDs harnesses use today read the same either
  way.
- A harness is at most 32 characters and a session id at most 128, so a name
  is at most 175 characters, under every filesystem's limit.

The helper throws on a harness or id the record schema would refuse.
Re-importing writes a new version of the same item.

### Tags

The extension's output spec sets `type: agent-session`, which replaces the
writer's own `type: resource`. Output-spec tags are the same for every item,
so the per-session tags are passed on each write instead: `swampUserId`, and
the four list tags from `agentSessionTags(record)`:

| Tag               | Value                                                           | Used for                                  |
| ----------------- | --------------------------------------------------------------- | ----------------------------------------- |
| `startedAt`       | the record's `startedAt` as `toISOString()` writes it           | newest-first sort (swamp-club#4177)       |
| `parentSessionId` | the parent's id; absent on a top-level session                  | listing top-level sessions, and children  |
| `headless`        | `"true"` when `invocation` is `headless`, else `"false"`        | the headless filter, in the query         |
| `summary`         | compact JSON matching `AgentSessionSummaryV1Schema`             | the list row                              |

`startedAt` is rewritten so every tag has milliseconds and sorts in time
order as a string. The extension derives the tags from the record so they
cannot drift from it.

### The list summary

`agentSessionSummary(record)` holds `repo`, `harness`, `harnessVersion`?,
`invocation`, `wallMs`, `activeMs`, `turns`, `calls`, the `swamp`, `bypass`,
`neutral` and `unlabeled` counts, `failedCalls`, `subagents`, the four
`tokens` totals and `findings` per severity.

- Counts cover the session's own calls only. The page sums a session's
  children through the children query; `subagents` counts the session's
  subagent calls, so the list can show "3 subagents" without that query.
- `wallMs` is the latest turn or call end. `activeMs` adds up turn durations,
  counting a negative one as zero. `activeMs` and the token totals stop at
  `Number.MAX_SAFE_INTEGER`, so an absurd record still gives a summary the
  page can read.
- Every string in it is bounded, and `readAgentSessionSummary` refuses a tag
  over 4096 characters before parsing it.

### Finding sessions

The page lists sessions with the dashboard's existing `data.query`. It needs
no new filter:

- top-level sessions: `AGENT_SESSION_TOP_LEVEL_PREDICATE`, the type tag with
  no `parentSessionId`;
- one session's children: `agentSessionChildrenPredicate(id)`, which refuses
  an id the record schema would refuse, so only an id reaches the predicate;
- every session: `AGENT_SESSION_QUERY_PREDICATE`.

A list query passes `AGENT_SESSION_LIST_SELECT`, which reads only the data
name, the owning behavior's name and tags; `data.get` needs the behavior name
to open a listed session. With a predicate over tags, the query then never
loads a record body. The list pages newest first with
`sort: { field: "tags.startedAt", direction: "desc" }` and a `limit`, and asks
for each later page with the `nextCursor` the previous one returned
([data-query.md](../enablers/data-query.md#sorting-and-paging---sort---cursor)).
The sort reads the tag in SQL, so it loads no body either, and the type tag
equality in the predicate pushes down to the catalog's `data_type` column, so a
limit-1 probe for any session does not scan the whole catalog. Without a select, `data.query` loads the body of every record it
returns. `data.query` drops records the viewer may not read before it applies
the limit, so a page of results always reflects readable sessions.
`data.search` also takes a tags filter, but it applies its limit before its
read filter, so the page does not use it.
`integration/agent_session_discovery_test.ts` pins this contract.

A tag is a hint for finding records; it does not prove who wrote one, and a
summary can disagree with its record. The page shows the summary in the list,
and always validates a record with `readAgentSessionRecord` when the session
is opened.

## Versions

`schemaVersion` is in every record from version 1. `readAgentSessionRecord`
never throws, so one bad record cannot fail the page. A record it cannot read
is skipped with a note. The note names field paths and never field values; the
one value it repeats is the record's `schemaVersion`, once that is known to be
an integer:

| Reason    | When                                                    | Note tells the viewer to |
| --------- | ------------------------------------------------------- | ------------------------ |
| `newer`   | the version is above what this swamp reads              | upgrade swamp            |
| `older`   | a version this swamp no longer reads                    | re-import the session    |
| `invalid` | no integer `schemaVersion`, or content fails the schema | report the bad record    |

The page shows how many sessions it skipped and why. It never prompts for a
re-import.

Version 2 is current, and version 1 is no longer read: a version 1 record is
`older`. No version 1 data existed outside its authors' machines while the
extension was unpublished, so nothing is migrated. A new field, even an
optional one, is a new version, because each version refuses fields it does
not name. The summary schema has its own version; a summary tag that does not
match the current one reads as `undefined`, and the page opens the record
instead.

**Reading it in the page.** The dashboard imports this module and `zod`
rather than copying the reader: the module has no Deno or Node APIs, and a
copy would drift on the rules the schema refines. It does so through one
adapter, `packages/dashboard/src/lib/agent_sessions/record.ts`, and
`integration/dashboard_core_import_rules_test.ts` pins that this is the only
core module the bundled dashboard imports, and that the module imports
nothing but `zod`.

## The page

The dashboard's Agent sessions page (swamp-club#4155) sits under Operations
with a Preview chip. Its requests are in
`packages/dashboard/src/client/agent_sessions.ts`, and
`integration/agent_sessions_page_test.ts` sends them through serve's handlers.

- **Visibility.** The sidebar item shows only when one `data.query` with
  `AGENT_SESSION_TOP_LEVEL_PREDICATE` and a limit of 1 finds a session the
  viewer can read. That departs from the faded "Off" items on purpose: with
  no session data there is nothing to turn on. The check runs when the
  dashboard loads and when it reconnects, so sessions imported while it is
  open show after a reload. Hiding is not access control: the route answers
  a direct URL, and every request it sends is read-gated.
- **The list.** Top-level sessions come from tags alone. The page reads the
  newest 1,000 with `sort: tags.startedAt desc` (swamp-club#4177) and, when
  that window filled its limit, offers to read the next 1,000 older with the
  `nextCursor` it returned. Column sorts, the headless filter, the totals and
  the 50-row pages cover the sessions loaded, and the page says so while
  older ones remain. Sorting by a column in SQL is not possible: the figures
  live inside the `summary` tag's JSON, and `data.query` sorts by a whole tag
  as a string. A re-read of the newest window (a reconnect, a retry) drops
  the older windows.
- **A session.** Opening one reads its record with `data.get`. Its subagents
  are listed from tags (`agentSessionChildrenPredicate`, limit 500), and a
  subagent's record is read when its call is opened or its findings are
  loaded. A subagent opens under the call that started it, at full detail.
  Findings are only read, never computed: the opened session's and its
  loaded subagents' are shown together, most severe first.
- **Skips.** A record that does not read shows its note, never its content.
  A summary tag that does not read leaves the row's numbers blank; the
  session still opens.
- **Large turns.** A turn with more than 100 calls draws only the rows in
  view.

## Access

Today a data read is authorized on the behavior that owns the data: its name
and tags, not the data item's own tags. A grant can therefore show or hide a
whole importer's sessions, but cannot yet say "only your own". The
`swampUserId` tag is written now so that a later access change can let a
condition compare it with `principal.sub`, with no change to the record. That
works when serve uses OAuth. Under `--auth-mode token` a user principal is a
username, so that mode would need a mapping.

## Sync

Session data is written under `data/`, which is in
`DEFAULT_DATASTORE_SUBDIRS`, so it syncs to a shared datastore by default.
That is accepted while the extension is unpublished, because only its authors
have session data. It must be settled before the extension is published,
together with the exploration's decision on where traces live. A user can
already keep sessions out of a shared datastore with an `exclude` pattern in
its config.
